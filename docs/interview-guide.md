# Interview Guide

## 30-second explanation

LedgerLeak is a synthetic DNS exfiltration detection lab that combines Sysmon, Windows logs, Zeek, Wireshark, and Splunk to show how a SOC analyst correlates endpoint and network telemetry to identify suspicious DNS tunneling from a finance workstation.

## 60-second explanation

I built LedgerLeak to showcase how detection engineering works in a realistic SOC workflow. The project models a Northstar Financial Operations workstation that begins generating encoded DNS queries to a lab-controlled domain. By correlating login activity, process creation, DNS frequency, entropy, and baseline deviation, the investigation shows how analysts move from raw packet evidence to a final incident assessment with MITRE mapping and an executive report.

## 3-minute technical explanation

The lab starts with synthetic telemetry generated in Python to mimic a legitimate corporate environment. Normal DNS traffic from several workstations is mixed with a suspicious burst from FIN-WS-014, the host assigned to finance analyst npatel. The suspicious host creates a process lineage that includes Excel followed by PowerShell, then begins generating long encoded subdomains to `lab-sync.test`.

The Python analytics layer computes DNS feature values such as query length, entropy, unique subdomain count, and queries-per-minute. Those metrics are converted into a risk score based on configurable thresholds. Splunk then correlates the DNS analytics with Sysmon and Windows login events to build a timeline and show how the host, process, user, and network signals fit together.

The packet capture is reviewed in Wireshark to isolate DNS queries from the affected host, and Zeek converts the capture into structured logs that are easier to analyze in a SIEM. The result is a portfolio-ready project that demonstrates detection engineering, investigation workflow, baseline analysis, and incident reporting.

## Why did you build this?

I wanted a project that looked like a realistic SOC investigation rather than a toy malware demo. The goal was to show how analysts correlate endpoint, network, and identity evidence into one coherent story.

## Why Splunk?

Splunk is a natural fit because it supports high-volume correlation, dashboarding, and analyst workflow. It also gives the project a realistic SIEM-style operational lens.

## Why Wireshark?

Wireshark is the best way to show packet-level evidence and inspect the actual query names, timestamps, and transport behavior that cyber analysts review during incident response.

## Why Zeek?

Zeek converts packet data into structured logs, making it easier to ingest results into Splunk and explain how raw network evidence becomes analyst-friendly telemetry.

## Why use Sysmon?

Sysmon gives the most informative process and network metadata for Windows environments. It directly supports parent-child process correlation and the investigation of command execution around the suspicious DNS behavior.

## Why calculate entropy?

Entropy helps identify strings that look random or algorithmically generated. DNS labels that are encoded or generated by a tool often have unusually high character diversity compared to human-readable names.

## Why isn't entropy alone enough?

High entropy appears in some legitimate contexts, and a single indicator can create false positives. Correlation with volume, query length, rare domain destination, and process behavior is much more reliable.

## How did you reduce false positives?

I limited the risk score to multiple correlated signals and used baseline comparisons. Long labels and high entropy are treated as supporting data rather than a binary verdict.

## How did you correlate endpoint and network telemetry?

The project uses a common host, user, and time window to tie together process creation, Windows login events, and DNS query data. The analyst can explain the sequence of cause and effect rather than looking at isolated artifacts.

## What would you improve in production?

I would add more realistic baselines, external threat intel, response automation, and a richer SIEM alert workflow. I would also integrate a real packet extraction pipeline and more advanced anomaly modeling.

## What did you learn?

The biggest lesson is that strong detection engineering depends on correlation and explainability. A good SOC analyst does not rely on a single log field; they build a story from multiple sources, then document that story clearly.
